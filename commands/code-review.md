# Code Review 命令

> ⚠️ **核心原则**：
> - 拉取 release 分支时：临时切换到 release → 更新代码 → 切回原分支
> - 对比代码时：**确保在原分支上**对比与 release 分支的差异
> - 必须保存并恢复当前分支名称，保证审查的是当前开发的代码

---

## 使用方法

```bash
/code-review [仓库名列表]
```

**仓库名参数**（可选，多个用空格分隔）：

- `dbh` → 对应 `src/pages/home`
- `dbi` → 对应 `src/pages/intelligence`
- `dbg` → 对应 `src/pages/globalpedia`
- `dbu` → 对应 `src/pages/user-center`

**示例**：

```bash
# 审查所有仓库（默认）
/code-review

# 审查指定的仓库
/code-review dbh dbi

# 只审查一个仓库
/code-review dbh
```

---

## 执行流程

### 步骤 1：解析仓库名参数

根据传入的参数确定需要审查的仓库列表：

- 如果未传入参数，默认审查所有 4 个仓库
- 如果传入了参数，只审查指定的仓库

仓库名映射关系：
| 参数名 | 完整路径 |
|--------|----------|
| dbh | src/pages/home |
| dbi | src/pages/intelligence |
| dbg | src/pages/globalpedia |
| dbu | src/pages/user-center |

### 步骤 2：拉取最新代码

依次拉取每一个需要审查的仓库的最新 release 分支代码：

```bash
# 注意：不要执行 git submodule update --init --recursive
# 这个命令可能会把其他未指定的子模块切换到非预期的状态
# 直接在指定的子仓目录中操作即可

# 拉取指定子仓的 release 分支（更新本地 release 分支）
# 注意：只处理指定的 4 个仓库，其他仓库不受影响
for repo in $REPOS; do
  cd "src/pages/$repo"
  # 1. 保存当前分支名称
  CURRENT_BRANCH=$(git branch --show-current)
  echo "[$repo] 当前分支：$CURRENT_BRANCH"

  # 2. 切换到 release 分支并更新到最新
  git checkout release
  git pull origin release

  # 3. 切换回原来的分支
  git checkout "$CURRENT_BRANCH"

  cd -
done
```

> ⚠️ **重要说明**：
> - 此流程会临时切换到 release 分支更新代码，但**最后会切回原分支**
> - 必须先用变量保存当前分支名称，确保能正确切回
> - 最终的代码对比是在**原分支**上进行的，保证审查的是当前开发的代码
> - **只处理指定的 4 个仓库**（dbh、dbi、dbg、dbu），其他子仓库不会被此脚本影响

### 步骤 3：获取代码变动内容

依次对比每一个仓库当前分支与本地 release 分支的代码变动，总结变动内容：

```bash
for repo in $REPOS; do
  cd "src/pages/$repo"
  # 确认当前分支（应该是在步骤 2 切回来的原分支）
  git branch --show-current

  # 当前分支相比 release 分支的变动（即将合并到 release 的代码）
  git diff release..HEAD --stat
  git diff release..HEAD

  cd -
done
```

> ⚠️ **重要说明**：
> - 此时每个仓库应该已经切回原分支（由步骤 2 保证）
> - `git diff release..HEAD`：当前分支有但 release 没有的变动（即将合并的）
> - 代码审查只关注这个方向的变动

### 步骤 4：执行代码审查

依次对每一个仓库的代码变动内容进行代码审查：

**审查对象**：当前分支 → release 分支 的变动（即将合并到 release 的代码）

审查重点：

#### 4.1 代码规范与风格

- **命名规范**：文件/目录/变量/类型/组件命名是否规范
- **代码格式**：缩进（2 空格）、大括号位置、行长度、空格和换行
- **注释质量**：解释"为什么"而非"做什么"，无冗余注释和无用代码
- **语法特性**：优先使用 ES6+ 特性
- **TypeScript**：接口以 I 开头、类型以 T 开头、分号结尾、显式类型
- **导入顺序**：外部库 → 内部工具 → 组件 → 样式；禁止 lodash，使用 lodash-es
- **React**：事件以 handle 开头、状态命名清晰、不直接修改 state
- **样式**：BEM + kebab-case，禁止全局样式、禁止全局修改 tea 组件样式、禁止修改字体

#### 4.2 逻辑与设计

- **功能实现**：逻辑正确完整，考虑边界条件
- **代码结构**：模块化、组件化，遵循单一职责原则
- **重复代码**：抽取公共组件、函数或工具类
- **复杂度**：避免复杂逻辑，条件判断清晰

#### 4.3 性能与安全

- **性能隐患**：避免重复渲染、低效循环、内存泄漏
- **安全漏洞**：XSS 防护、CSRF 防护

#### 4.4 可维护性与最佳实践

- **错误处理**：异步操作的 try/catch 处理
- **硬编码**：提取常量或配置
- **依赖管理**：复用已有组件和工具函数

### 步骤 5：输出审查结果

将审查结果输出到 `databrain-main-frame/code-review` 目录下。

**输出文件格式**：

```markdown
# Code Review 报告

**审查时间**: YYYY-MM-DD HH:MM:SS
**审查仓库**: [仓库名列表]

---

## 问题统计

| 仓库 | 高危 | 建议 | 优化 | 总计 |
|------|------|------|------|------|
| home | 0 | 0 | 0 | 0 |
| ... | ... | ... | ... | ... |
| **总计** | 0 | 0 | 0 | 0 |

---

## 详细问题清单

### [仓库名]

#### [问题级别] 问题

| 文件路径 | 行号 | 问题描述 | 修改建议 |
|----------|------|----------|----------|
| xxx.tsx | L12-L15 | 描述 | 建议 |

---

## 代码变动摘要

### [仓库名]

[该仓库的代码变动内容总结]
```

### 步骤 6：结束审查流程

审查完成后，输出总结信息：

- 审查完成的仓库列表
- 问题总数统计
- 审查结果文件路径

---

## 注意事项

1. 临时切换到 release 分支更新后，必须正确切回原分支
2. 对比差异时保持在当前分支执行 diff（对比 HEAD..release）
3. 审查结果文件以时间戳命名，便于追溯
